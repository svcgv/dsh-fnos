# 浏览器接入：部署安全边界与验收

本目录及相邻浏览器组件均为实验原型，尚未安装或启用；当前不能用于不可信网页或秘密。独立 Chromium、私有 CDP 管道和离线文件系统的实验结果不能证明互不信任的飞牛用户之间已隔离。未验证 ARM64 或 Chromium 各层沙箱的实际状态。

## 现有部署的边界

- `src/harness.ts` 为每个飞牛 UID 设独立工作目录和环境，但启动 Harness 时没有切换宿主 UID/GID；当前多个工作区的代码以相同系统账号执行。每个工作区的目录、Agent scope、0700 目录和 CDP 管道都不能区分同一系统账号的执行者。
- 离线浏览器使用独立网络、挂载、PID 和用户命名空间，并实验性地切换根文件系统。受控测试确认指定的宿主目录与自建路径型 Unix socket 在隔离环境内不可见。这不证明同 UID 的其他宿主进程无法访问或干扰浏览器控制端和工作区，也不证明内核或浏览器不存在逃逸漏洞。
- 路径 socket 的权限和 `SO_PEERCRED` 使用宿主系统身份，不能将相同 UID 的进程区分为不同飞牛用户；抽象 socket 的隔离还依赖网络命名空间。`kernel.yama.ptrace_scope=1` 不等价于租户隔离，也不能据此断言同 UID 进程一律能够或不能 ptrace 其他进程。
- 当前服务处于应用中心共享的 cgroup，应用账号不能自行管理子 cgroup。进程组及 `unshare --kill-child` 不保证父进程 SIGKILL 或宿主故障后整个进程树和临时数据均被回收。不得清理整个应用中心共享 cgroup。
- 只给一个飞牛用户开启浏览器也不自动安全：如果同机其他不受信任工作区仍能以相同宿主 UID 执行，仍可威胁该用户。若没有独立执行身份，现有版本只能定位于整机同一信任域。

## 若要支持互不信任用户

需要管理员另行审查并授权宿主部署改造，而不是仅改变浏览器插件：

1. 保留可信网关负责认证；通过固定功能的受控启动服务管理租户。请求不能指定任意可执行程序、环境、挂载或 systemd 属性。租户代码不能以网关身份运行，也不能访问网关管理 socket。
2. 为每个并发的不可信租户分配独立、非登录系统身份，隔离整个 Harness，包括 shell 和插件，而非只隔离 Chromium。用户目录、凭据和控制 socket 必须按该身份隔离；不得借用带管理员权限的飞牛账号。稳定映射、容量上限、状态目录所有权和迁移方式均需明确；无法满足时拒绝启动，不回退到共享 UID。
3. 由管理员配置独立的服务监督和专属 cgroup，覆盖整个租户进程树，限制资源并在停止时清理进程。定义网关异常后的租约失效和停止流程；禁止租户迁移 cgroup。不要授予通用 sudo、Docker 组或任意 systemd 管理权限。
4. 保留原有用户 profile 内容，不自动安装插件或改写配置。状态目录迁移或所有权变更必须由管理员明确批准，并验证原数据完整性。
5. 网络仍须默认拒绝，并另行证明实际连接目标、子请求、重定向及域名授权。现有 CONNECT/SNI 代理无法看到加密 HTTP authority，不能保证共享 CDN 上的逐站点授权。不能将固定测试端点实验当作通用网站访问能力。

## 上线前的隔离验收

使用两个独立的测试租户和自建数据进行：验证 A 无法读取 B 的文件、向 B 的测试进程发信号或附加调试、连接 B 的路径或抽象控制 socket；验证非预期退出后专属 cgroup 归零和临时数据回收；验证原 profile 不变、资源受限、异常时拒绝而不降级。旧共享 UID 的不受信任执行者应先停止，否则新边界尚未成立。验收不使用真实用户凭据或网页。

这些要求是设计方向，不是已完成的实现、运维授权或安全审计。无宿主权限改造时只能继续受限实验，不能声称实现多租户安全隔离。
